Release builds, synthetic libraries, per-run isolated application state. The original is develop @ 745ef82; GPUI includes the fullscreen handoff and volume-focus fixes. Production databases, sessions, caches, preferences and the running production instance were not used.

CPU and memory are directly compared across the same visible workloads. WebView requestAnimationFrame callbacks and Metal presentation timestamps are different instruments. Their cadence appears separately and does not prove a universal WebKit frame-rate cap.

Frame cadence and renderer work

Active scrolling uses 1,080 logical pixels/second and reverses every eight seconds. Both apps use their native virtual lists and ordinary rendering paths. The adapter feeds DOM scroll positions in the original and pointer scroll events in GPUI. This is a controlled scrolling workload, not a physical trackpad or input-to-photon measurement.

What changed for the two reported bugs

  • Fullscreen: paint the requested player scene before asking AppKit to animate the native transition. Check the requested target state, so entering the player from an already fullscreen library does not toggle the window out of fullscreen. Superseded transition requests and old-account requests are rejected.
  • Volume: the popup owns a focus scope. A focused descendant or active slider drag keeps it open even when the pointer leaves. Focus departure restarts normal dismissal, with a second guard when the delay expires. Dialog entry still dismisses the popup immediately.

Method and reproducibility

Sampling

  • Fresh process and temporary backend state for every launch; shared OS filesystem/shader caches remain warm. Run order alternates between apps, and state order reverses on even repetitions.
  • Fixture readiness is verified before sampling. Startup is process launch → detection of an adapter marker after a populated render; polling adds up to roughly 10 ms plus filesystem/scheduling delay. It is not first pixel or cold-boot startup.
  • Static states do not schedule benchmark animation frames. Active states collect diagnostics over roughly 8.5 seconds. Those diagnostics and CPU windows overlap but are not sample-perfect.
  • Process attribution combines descendants and newly appearing WebKit XPC helpers. Unrelated simultaneous WebKit launches can confound it. The report retains process identities and counts in raw data.

Comparable inputs

  • Nominal desktop native window: 1,200 × 800 logical units; compact: 390 × 844. WebView dimensions exclude the native titlebar; GPUI’s viewport includes its titlebar inset. Fullscreen uses the same display.
  • Paused track 5 at 1:23 / 3:16. Synthetic artwork: 64 distinct 512 × 512 PNGs, repeated across the library. No production artwork was copied.
  • Fullscreen-playing uses the same generated 25 ms loudness/onset/bass/mid/treble profile and a synthetic playing snapshot. It renders animation without decoding, networking or audible output.
  • Search “005” is a filter workload; open search is a scrolling workload. Settings and navigation measure the settled overlay with blur enabled.
Opening timing is diagnostic, not a fair latency ranking

The adapters schedule different numbers of callbacks and the original fullscreen API resolves at a different point in the OS transition. The raw opening callback values are retained for debugging, but no original-versus-GPUI overlay latency ratio is claimed. A high-speed camera or common event-to-present instrumentation would be needed for a reliable input-to-photon comparison.

What this report does not establish

Authenticated hydration; Telegram transport, ID3 download or streaming throughput; codec/audio-output CPU; audible underruns; device seek latency; GPU utilization or power in watts; cold OS cache startup; hours-long memory behavior; Android/Windows/Linux performance; installed/installer/update size. macOS RSS includes shared mappings and is not unique physical memory. CPU readings for the production app are not included or modified.

The original already used Rust services for networking, SQLite and audio. Replacing the UI does not imply those services became faster. A smaller RSS or lower CPU value also does not prove lower total energy when the new app presents more frames.
